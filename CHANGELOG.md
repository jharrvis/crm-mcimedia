## [Unreleased]

### Ditambahkan
- Sinkronisasi HestiaCP **bertahap per batch** (t_dcccffd9): tombol **Sinkron** di halaman Server Hestia (`/hestia/servers`, daftar & detail) tidak lagi mengirim satu form POST panjang yang rawan gateway timeout (kasus nyata: 59 akun pada satu server). Alur baru: `POST /hestia/servers/{server}/sync/start` membuat **sesi** (daftar akun ditarik sekali → total akun & angka progress), lalu browser memanggil `POST .../sync/batch` berulang — default **10 akun per batch** (bisa diatur lewat `batch_size`, maksimum 50) — sampai server membalas `done: true`. Frontend menampilkan **progress bar** ("Menyinkronkan akun 20/59… 34%"), spinner, status counter (domain ditarik/baru/diperbarui), menonaktifkan **semua** tombol sync selama proses (anti double-click & anti sesi paralel), dan menampilkan hasil akhir sukses/gagal + jumlah akun tersinkron + daftar akun gagal **tanpa reload halaman** (tautan "Muat ulang halaman" disediakan untuk menyegarkan angka tabel). Setiap request memakai timeout 120 dtk (≥ 60 dtk) dan **retry otomatis**; batch bersifat idempotent (`next_offset` hanya maju setelah batch tersimpan) sehingga retry tidak menggandakan upsert. State sesi disimpan di tabel baru `hestia_sync_batches`; satu sesi menulis satu baris `hestia_sync_logs` seperti sync biasa sehingga riwayat `/hestia` tidak berubah. Tanpa JavaScript, form POST lama tetap berfungsi (fallback `<noscript>`).
- Ketahanan sync bertahap (t_dcccffd9): kegagalan satu akun (mis. timeout API) dicatat sebagai error per akun dan **tidak menghentikan batch**; **penonaktifan akun yang hilang dilewati** selama masih ada akun gagal ditarik (daftar `seen_keys` yang tidak lengkap tidak boleh mematikan akun yang sebenarnya masih ada). Sesi berstatus gagal hanya bila tidak ada satu pun domain yang berhasil ditarik. Sesi "running" yang ditinggalkan (tab ditutup di tengah proses) otomatis dibatalkan saat sesi baru dimulai untuk server yang sama, dan request batch yang diulang setelah sesi selesai mengembalikan keadaan akhir apa adanya. Modul browser `resources/js/hestia-sync.js` + tes `node --test` untuk logika progress, retry/timeout, dan wiring tombol; 13 tes feature baru di `tests/Feature/Hestia/HestiaBatchSyncTest.php`.
- Multi-server sinkronisasi HestiaCP (F4-12): tabel `hestia_servers` (satu baris = satu panel HestiaCP, mis. **sg2**, **YIARI**, **PA Salatiga**) dengan kolom `name`, `code` (slug stabil & unik), `host`, `port`, `scheme`, `verify_ssl`, `timeout`, `is_active`, `notes`, dan penanda hasil sync (`last_sync_at`, `last_sync_status`, `last_synced_at`, `last_sync_message`). Kredensial (`user`, `password`, `access_key`, `secret_key`) disimpan pada kolom `credentials` sebagai JSON **terenkripsi** (cast `encrypted:array`, pola F4-5 `DomainProvider`) — tidak pernah ditampilkan utuh di UI, tidak pernah ditulis ke log atau `hestia_sync_logs`.
- UI manajemen server di `/hestia/servers` (menu **Server Hestia**, di bawah "Sinkron Hestia"): daftar server (kode, endpoint, status kredensial, jumlah akun, sync terakhir, status), tambah/ubah/hapus, tombol **Uji** (probe read-only `v-list-users`), tombol **Sinkron** per server, dan halaman detail per server berisi akun hasil sinkronisasi + riwayat sync. Form edit tidak pernah mengirim nilai rahasia ke browser — field kosong berarti "pertahankan nilai lama". Hapus server **tidak** menghapus akun/layanan (`nullOnDelete`).
- Loop sinkronisasi multi-server: `HestiaSyncOrchestrator` menentukan server aktif lalu memanggil `HestiaSyncService::sync($server)` satu per server. **Kegagalan satu server tidak menghentikan server lain**; tiap server punya baris `hestia_sync_logs` sendiri (`hestia_server_id`) dengan sumber/label sendiri. `HestiaClient::__construct(?array $config = null)` menerima konfigurasi per-server (tanpa argumen tetap membaca `config('crm.hestia')`, jadi DI Laravel tidak berubah).
- Perintah `hestia:sync` diperluas: tanpa opsi menyinkronkan **semua server aktif**, `--server=<kode|nama>` menyinkronkan satu server, `--list` menampilkan daftar server + status kredensial & sync terakhir. Tetap terjadwal harian pukul 06:30 via `bootstrap/app.php`. Cara pasang & contoh lengkap di `docs/DEPLOY.md`.
- `HestiaServerSeeder` membuat 3 entri awal (`sg2`, `yiari`, `pa-salatiga`) **nonaktif dan tanpa kredensial** — tidak ada host/kredensial nyata di repo; admin mengisinya lewat UI. Idempotent & non-destruktif (`firstOrCreate` per `code`): menjalankan ulang tidak mengubah server yang sudah dikonfigurasi. Jalankan manual via `php artisan db:seed --class=HestiaServerSeeder`.
- Filter per server di `/hestia` (dropdown: Semua / tiap server / Environment), kolom **Server** pada tabel akun belum dipetakan & seluruh akun, serta kolom **Sumber** pada riwayat sinkronisasi. Parameter query string rusak (`srv:<id>` tak dikenal, input non-numerik) diabaikan tanpa error.
- Factory `HestiaServerFactory` (state `withPassword()` / `withAccessKey()`) + 33 tes feature `tests/Feature/Hestia/HestiaMultiServerTest.php` (CRUD UI, enkripsi at-rest & kebocoran, isolasi sync, idempotensi per server, domain sama di dua server, `--server`, kill switch, uji koneksi, read-only).

### Diubah
- `HestiaSyncService` (t_dcccffd9): logika tarik + upsert satu akun diekstrak ke `syncUser()` (dipakai `sync()` penuh maupun `HestiaBatchSyncService`) dan penonaktifan akun hilang dibuka lewat `deactivateMissing()` — satu jalur upsert untuk kedua mode, tidak ada implementasi kembar. Perilaku sync penuh (command `hestia:sync`, form POST lama) tidak berubah; seluruh suite (790 tes) hijau.
- **Isolasi sinkronisasi per server (perbaikan bug)**: `HestiaSyncService::deactivateMissing()` kini WAJIB discope dengan `HestiaAccount::scopeForServer()`. Tanpa scope ini, sinkronisasi server `sg2` akan menonaktifkan seluruh akun server `YIARI` yang domainnya tidak ada di sg2. Kedua kasus tercakup tes regresi (sudah diverifikasi lewat uji mutasi: menghapus scope membuat kedua tes gagal dengan akun YIARI berubah jadi `inactive`).
- Kunci eksternal akun menjadi **server-scoped**: `HestiaAccount::keyFor($hestiaUser, $domain, ?$serverCode = null)` menghasilkan `srv:<code>:dom:<user>:<domain>` untuk server terkelola dan tetap `dom:<user>:<domain>` untuk path environment. Parameter baru ditaruh **terakhir & opsional** → signature lama kompatibel penuh. Dua server dengan user+domain identik tidak lagi saling menimpa akun.
- `HestiaSyncService::sync()` kini menerima `?HestiaServer $server` sebagai parameter **pertama** dan `?HestiaClient $client` sebagai kedua (sebelumnya hanya client opsional). Pemanggil lama `sync()` tanpa argumen tetap kompatibel.
- `crm.hestia.enabled` (`HESTIA_ENABLED`) menjadi **kill switch global**: `false` mematikan sinkronisasi untuk environment maupun seluruh server UI (sebelumnya hanya untuk path environment). Bila minimal satu server UI aktif, proses sync memakai server UI dan mengabaikan host/kredensial `.env` agar tidak terjadi akun ganda dari sumber yang sama; banner biru di `/hestia` menandai kondisi tersebut. Path environment F3-1 tetap berfungsi sebagai fallback bila belum ada server aktif.
- Migrasi F4-12 bersifat **aditif saja** (`hestia_server_id` nullable di `hestia_accounts` & `hestia_sync_logs`, tanpa rewrite data) → data hasil sinkronisasi F3-1 yang sudah ada tidak tersentuh. Migrasi F3-1 tidak diubah.
- `/hestia` — tombol utama berubah label "Sinkronkan sekarang" menjadi **"Sinkronkan semua server"** dan menampilkan ringkasan per sumber; partial failure dilaporkan sebagai error yang menyebut server mana yang gagal.
- Paket, kuota, dan status di halaman Sinkron Hestia (F4-13): kolom `disk_used`, `disk_quota`, `suspended`, dan `user_suspended` ditambahkan ke `hestia_accounts` (migrasi aditif `2026_10_07_200001`). Nilainya dipecah dari payload Hestia yang **sudah** tersimpan di kolom `raw` sejak F3-1 — **tidak ada panggilan API baru** dan sifat read-only sinkronisasi tidak berubah. Sumber field diambil dari sumber HestiaCP: `U_DISK` (MB dari `du -shm`), `DISK_QUOTA` (MB, ada di level paket/user — tidak ada di payload web domain), serta `SUSPENDED` yang dipisahkan antara level web domain dan level akun Hestia. Kelas baru `HestiaQuota` menormalkan satuan/flag (nilai tak terisi atau rusak jadi `null` = "tidak diketahui", bukan `0` atau `false` hasil tebakan).
- UI `/hestia` (F4-13): kolom **Paket** dan **Pemakaian disk** (bar persentase + `512 MB / 1,0 GB (50%)`, warna hijau < 80% / kuning ≥ 80% / merah ≥ 100%) di tabel akun dan di daftar akun yang belum dipetakan; lencana status **Suspend** (kuning) membedakan akun yang benar-benar disuspend dari akun "tidak aktif" karena hilang/tidak terlihat di Hestia, dengan keterangan tambahan bila akun Hestia pemiliknya yang disuspend. ### Diperbaiki
- `/hestia`: kuota yang **belum dilaporkan** Hestia (`disk_quota` null) tidak lagi ditampilkan `∞`. Sebelumnya `∞` (tanpa batas, `DISK_QUOTA = 0`) dipakai juga untuk nilai null — yang berarti mengklaim paket tak terbatas tanpa bukti dan membuat operator salah menilai kapasitas. Sekarang tiga keadaan dibedakan: angka, `∞` + keterangan "(tanpa batas)", dan `—` (belum ada data).
- `/hestia`: filter dan kartu ringkasan **Aktif** tidak lagi ikut menghitung akun yang sedang disuspend. Kolom `status` (F3-1) hanya berarti "terlihat pada sinkronisasi terakhir", sehingga sebelumnya bar berlabel "Suspend" bisa muncul di hasil filter "Aktif" dan ikut terhitung di kartu "Aktif". Ketiganya kini memakai scope `suspended()`/`notSuspended()` sehingga lencana, filter, dan angka kartu selalu sepakat.
- `/hestia`: pencarian domain/akun ber-underscore (mis. `my_domain.com`) kembali menemukan hasilnya. Wildcard di-escape tanpa klausa `ESCAPE` hanya berlaku di MySQL; di SQLite backslash dibaca sebagai karakter biasa sehingga hasilnya selalu kosong. Pola kini memakai `ESCAPE` eksplisit dan tetap di-bind sebagai parameter (user input tidak pernah masuk ke SQL).
